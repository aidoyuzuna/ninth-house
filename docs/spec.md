# Aries Tech Garden — 静的サイトジェネレーター 仕様書

Zettelkasten 方式のデジタルガーデンを公開するための、自作静的サイトジェネレーター（SSG）の仕様。

- 最終更新: 2026-09-14
- ステータス: 仕様確定（未決事項は §10 を参照）

---

## 1. 全体方針

| 項目 | 内容 |
|---|---|
| 開発方針 | スクラッチで自作する。既存SSGのカスタマイズはしない |
| 実装言語 | Node.js / TypeScript |
| ホスティング | Cloudflare Pages |
| 画像ホスティング | Cloudflare R2（バケットを直接公開。カスタムドメイン `image.ariestechgarden.com`） |
| 執筆環境 | Obsidian（フラットなVault、フォルダ階層なし） |
| サイト名 | Aries Tech Garden |

設計の通底する判断基準:

- **フォルダ階層を作らない。** 分類はタグだけで行う。
- **手動メンテを増やさない。** MOC・一覧・バックリンクはすべて自動生成する。
- **検索で見つかればよい。** リンクを辿れるかを根拠にした機能（孤立ノート検出など）は過剰要件とみなす。
- **機能は「入れるが最小限」で刻む。** 欲しい機能でも、リッチな実装は求めない。

## 2. コンテンツモデル

### 2.1 ノート

- Obsidian Vault 直下にフラットに配置した Markdown ファイル1本 = ノート1本。
- **ファイル名がタイトル**になる。フロントマターに `title` キーは持たない。
  - ファイル名は人間が読める日本語の説明的な文字列（例: `Obsidianのプロパティを整理する.md`）。
  - リネームしてもObsidianがリンクを自動更新し、Gitがrenameを検出するため、実運用上の破綻はないと判断。

### 2.2 フロントマター

6キーで確定。

```yaml
---
id:
create:
update:
tags: []
toc:
publish:
---
```

| キー | 生成元 | 内容 |
|---|---|---|
| `id` | Obsidian Linter が自動挿入 | タイムスタンプ型の一意ID（例: `202609131430`）。**公開URLの実体**（§3） |
| `create` | Obsidian Linter が自動挿入 | 作成日時。トップページの並び順と、ノートページの作成日表示に使う |
| `update` | Obsidian Linter が自動挿入 | 更新日時。ノートページの更新日表示に使う |
| `tags` | 手入力 | タグの配列。**タグの正規のソースはここだけ**（§2.3） |
| `toc` | 手入力 | `true` のときだけ目次を生成する。デフォルト `false` |
| `publish` | 手入力 | `true` のときだけビルド対象にする。デフォルト `false` |

- `id` / `create` / `update` は Linter が埋めるため、執筆者は触らない。新規ノート作成時は上記のフロントマターをテンプレートとして使う。
- `publish` のデフォルトを `false`（オプトイン）にしたのは、未完成のノートが誤って公開されるのを防ぐため。
- キー名は `created` / `updated` ではなく **`create` / `update`**（単数形・スペースなし）。Obsidian Linter 側の設定に合わせている。

### 2.3 タグ

- 階層タグをサポートする。区切りは `/`（例: `西洋占星術/ハウス/1ハウス`）。
- **フロントマターの `tags` だけが正規のタグソース。** 本文中のインライン `#tag` 記法はタグ集計・MOCに一切反映しない。
- 表記ゆれの正規化（trim、全角半角統一など）はビルド側で行わない。執筆時に統一する運用でカバーする。

### 2.4 公開制御

- `publish: true` のノートだけをビルドする。
- 非公開ノートは **HTMLファイル自体を生成しない。** 「生成はするが一覧から隠す」という中間状態は作らない。
  - Pagefind は生成済みHTMLをスキャンするため、検索インデックスからも自動的に除外される。
- 非公開ノートへの WikiLink は**そもそも書かない**という運用ルールにする。ビルド側での特別処理・警告ログは実装しない。
- 公開後に `publish` を外してリンク切れになるケースは稀と想定し、検出・警告は実装しない。実害は「クリックすると404」程度で許容する。

## 3. URL設計

**公開URLはフロントマターの `id`（タイムスタンプ）を使う。** ファイル名（日本語タイトル）はURLに出さない。

| パス | 内容 |
|---|---|
| `/{id}` | 個別ノート（例: `/202609131430`） |
| `/` | トップページ |
| `/about` | 自己紹介ページ |
| `/tag/{タグパス}` | タグページ（＝MOC） |
| `/search` | 検索結果ページ |
| `/404` | ノートが見つからないとき |

この設計の利点:

- IDは数字のみなので、`/search` や `/about` といった英字パスと衝突しない。
- ノートURLに日本語が入らないため、パーセントエンコードの問題が発生しない。
- ファイル名（タイトル）を自由にリネームしてもURLが変わらない。

補足:

- **WikiLink の変換**: 執筆時は Obsidian の流儀どおりファイル名ベースで `[[ノート名]]` と書く。ビルド時にファイル名 → `id` を解決して `/{id}` へのリンクに変換する。
- **タグページのURL**: 階層区切りの `/` 以外の日本語はそのまま維持し、URL構文上意味を持つ記号だけをエスケープする。

## 4. ページ仕様

### 4.1 トップページ `/`

1. 一言挨拶＋`/about` へのリンク
2. 最近書いたノート **5件**（タイトルと日付のみ。説明文は出さない）
3. 主要タグ（MOC）へのリンク

並び順は **`create`（作成日）の降順**。更新日ソートは採用しない — 大量の一括編集で `update` が荒れると、一覧が実態と噛み合わなくなるため。

### 4.2 個別ノートページ `/{id}`

上から順に固定:

1. **タイトル**（ファイル名）
2. **作成日／更新日** — 両方ともタイトル直下に目立つ形で表示する
3. **タグ** — 横並び。各タグは `/tag/{タグパス}` へのリンクとして機能させる（装飾ラベルではなく導線）
4. **目次（TOC）** — `toc: true` のときのみ
5. **本文**
6. **バックリンク一覧**

**TOC**

- フロントマターの `toc: true` で明示制御する。見出し数の自動しきい値では判定しない。
- 拾う見出しレベルは `##` と `###` の2階層。
- 表示位置は本文中の**最初の `##` 見出しの直前**。リード文がある場合はその下に入る。
- 常時展開。`<details>` 等の折りたたみは使わない。サイドバー固定表示も採用しない。

**バックリンク**

- 本文末尾に自動追記する。
- リンク元ノートの**タイトル＋作成日**を一覧表示する。スニペットは出さない。
- `data-pagefind-ignore` を付け、検索インデックスからは除外する（§6.2）。

### 4.3 タグページ `/tag/{タグパス}`

タグページが自動的に MOC（Map of Content）を兼ねる。手動キュレーションのMOCノートは作らない。

階層タグの表示範囲はハイブリッド方式:

1. そのタグに**完全一致**するノートを直接一覧表示する
2. **一つ下の子タグ**へのリンクを別セクションで表示する（子タグ配下の個別ノートはページ内に展開しない）
3. 3階層以上でも同じルールを再帰適用する

**関連タグ**

- 共起ベースで自動生成する。同じノートに一緒に付いているタグを頻度順に集計する。
- 表示は**上位5件まで**。
- 「AのページにBが出るならBのページにもAが出る」という対称性は、共起が対称な関係である以上、仕様として正しい挙動とする。
- 最低共起数の閾値は未決（§10）。

### 4.4 `/about`

独立パスとして持つ（トップページには統合しない）。掲載項目:

1. 自己紹介
2. サイトの方針＆ルール
3. 連絡先
4. 頒布同人誌（**リンク集のみ**）
5. 著作権など

頒布同人誌の詳細は `/about` には書かず、デジタルガーデン内の通常ノートとして執筆する（`publish: true` ＋ `頒布物` タグ）。`/tag/頒布物` が自動MOCとして一覧を兼ねる。

### 4.5 `/404`

「ノートが見つかりません」の一言＋トップページへのリンクのみ。検索ボックスは共通ヘッダーに常設されているため、404固有の検索UIは用意しない。

### 4.6 共通ヘッダー／フッター

- サイト名（トップへのリンク）
- 検索ボックス（全ページ常時表示）
- 🎲 ランダムノートボタン — 押すと公開ノートからランダムに1本開く。表示中のページは除外する
- ◐ 配色切り替えボタン（§7.1）
- 絵文字はOS依存で勝手に着色されるため、アイコンは **`currentColor` で塗るSVG線画**に統一する
- フッターに `© Aries Tech Garden`

## 5. Markdown処理

### 5.1 対応する記法

| 記法 | 扱い |
|---|---|
| 標準Markdown | 対応 |
| `[[WikiLink]]` | 対応。ビルド時にファイル名 → `/{id}` に変換（§3） |
| Callout `> [!note]` | 対応。ただし **note / warning / question など3〜4種類に絞る**。未対応の種類は note と同じ見た目にフォールバックする |
| LaTeX数式 `$...$` | 対応。**KaTeX** を使い、**ビルド時にサーバーサイドで静的HTMLへ変換**する（`katex` npm パッケージの `renderToString`）。クライアントへのJS/CSS配信は不要 |
| コードブロック | シンタックスハイライト対応。**shiki** でビルド時に静的HTMLへ変換する。クライアントへの追加JS配信は不要 |
| 画像 `![alt](url)` | 対応（§5.2） |
| インライン `#tag` | 記法としては壊さないが、タグ集計には一切使わない（§2.3） |

### 5.2 画像

- Obsidian の添付ファイルとしては扱わない。**Cloudflare R2 に手動アップロードし、本文には最初からR2の公開URLを標準Markdown記法で直書きする。**
  - 例: `![目次](https://image.ariestechgarden.com/Extra/image/...)`
  - `![[image.png]]` 形式のWikiLink画像埋め込みはサポートしない。
- R2バケットは直接公開する。Pages Functions 経由のプロキシ＋認可チェックは行わない（非公開ノートの画像まで厳密に秘匿したいわけではないため）。
- **リサイズ・変換はビルド側で行わない。** 執筆者が事前に変換して用意する。
- 推奨最大横幅は **1400px程度**（本文幅700px × Retina/@2x）。
- ダークモードで白背景画像が浮いて見える件について、自動反転・自動背景処理などの小細工はしない。許容する。

### 5.3 ライトボックス（画像拡大表示）

- **実装する。** 技術書の目次スキャンなど、拡大しないと読めない密度の高い画像を貼るユースケースがあるため。
- 機能レベルは**シンプル版**: クリックで画像を中央に大きく表示するモーダルのみ。ズーム・パン・前後ナビゲーション・キャプション表示は実装しない。
- **自前実装**する。fslightbox / GLightbox 等の既存ライブラリは、上記の絞り込んだ要件に対してオーバースペックのため不採用。

## 6. 検索

Cosense（Scrapbox）の二段階検索体験を参考にする。

### 6.1 入力中（ドロップダウン）

- **タイトルの部分一致のみ**をリアルタイムでドロップダウン表示する軽量インデックス。
- 「新規ページ作成」の提案のような機能は不要。

### 6.2 Enter押下後（`/search`）

- 専用の検索結果ページへ遷移する。
- **タイトル＋本文の両方**を検索する。本文ヒット箇所はハイライト付きスニペットで表示する。
- 実装は **Pagefind** を想定する。
- 検索対象は本文コンテンツ本体のみ。`data-pagefind-body` で明示指定し、自動生成されるバックリンクセクションは `data-pagefind-ignore` で除外する。

## 7. デザイン

### 7.1 配色

**Catppuccin** で統一する。サイトUI・コードハイライトの両方を同一パレットに揃える。

- ダーク: **Mocha**（デフォルト）
- ライト: **Latte**
- ヘッダーの ◐ ボタンでライト／ダークを切り替える。`<html data-theme="dark|light">` で制御する。
- Latte は正規のライトコードテーマとして成立しているため、ライトモードではコードブロックも明るく表示する（「ライトモードでもコードブロックだけ暗いまま」という妥協は不要）。

意味変数へのマッピング（モックで確定済み）:

| 意味変数 | Mocha | Latte |
|---|---|---|
| `--bg` | base `#1E1E2E` | base `#EFF1F5` |
| `--bg-raised` | surface0 `#313244` | `#FFFFFF` |
| `--bg-sunken` | mantle `#181825` | mantle `#E6E9EF` |
| `--rule` | surface1 `#45475A` | surface0 `#CCD0DA` |
| `--rule-soft` | surface0 `#313244` | crust `#DCE0E8` |
| `--ink` | subtext1 `#BAC2DE` | subtext0 `#6C6F85` |
| `--ink-strong` | text `#CDD6F4` | text `#4C4F69` |
| `--ink-quiet` | overlay1 `#7F849C` | overlay0 `#9CA0B0` |
| `--link` | sapphire `#74C7EC` | sapphire `#209FB5` |
| `--link-hover` | sky `#89DCEB` | blue `#1E66F5` |
| `--wikilink` | mauve `#CBA6F7` | mauve `#8839EF` |
| `--accent` | lavender `#B4BEFE` | lavender `#7287FD` |

- リンク系は sapphire（通常リンク）／ mauve（WikiLink）／ lavender（アクセント）の3系統に絞る。
- コードハイライトのトークン割り当て: comment = overlay0（italic）／ keyword = mauve ／ string = green ／ number = peach ／ function = blue ／ attr = teal ／ operator = sapphire ／ punctuation = text。

### 7.2 タイポグラフィ

- 日本語フォント: **Noto Sans JP**（Google Fonts CDN 配信）。
- `font-feature-settings: "palt" 1` のみ適用する。異体字切り替え等、より踏み込んだ字体制御は追求しない。
- 等幅フォントは特にこだわりなし。モックでは JetBrains Mono を使用（暫定、変更可）。

### 7.3 レイアウト

- 本文コンテンツエリアは **700px・中央寄せ1カラム**。

## 8. ビルドとデプロイ

```
Obsidian Vault
  └─(手動 git add / commit / push)→ GitHub
        └─(Cloudflare Pages 純正のGit連携で push 検知)→ 自動ビルド
              └─ ssg-build && pagefind --site dist
```

- **Obsidian → GitHub は手動でgit操作する。** Obsidian Git プラグイン等による自動commit&pushは使わない。
  - まとめてコミットした結果、複数ノートの「最終更新日」が同日に揃ってしまうズレは許容する。目安表示なので実害なしと判断。
- **デプロイトリガーは Cloudflare Pages 純正のGit連携。** GitHub Actions は組まない。
- ビルドコマンドは「自作SSGのビルド → Pagefindのインデックス生成」の順に連結する。

## 9. 実装しないもの

判断の根拠ごと残しておく。再検討時にここを見る。

| 項目 | 理由 |
|---|---|
| グラフビュー | 閲覧者に不要と判断 |
| 手動キュレーションのMOCノート | タグページが自動MOCを兼ねるため。手動メンテの「しんどさ」を避ける |
| 孤立ノート（Orphans）の検出・一覧 | 検索とタグページで発見できるため、孤立状態そのものが実害を持たない |
| ノート埋め込み（トランスクルージョン） | スコープ外 |
| Mermaid図 | スコープ外 |
| `![[image.png]]` 形式の画像埋め込み | R2直書き運用に統一したため（§5.2） |
| タグ表記ゆれのビルド時正規化 | 執筆時に統一する運用でカバーする |
| 非公開ノートへのリンク切れ検出・警告ログ | 発生頻度が低く、実害も404止まり。気づいたら手動で直す |
| ビルド側での画像リサイズ・変換 | 事前に変換して用意する運用 |
| ダークモードでの白背景画像の自動処理 | 浮いて見えても許容 |
| 検索ドロップダウンの「新規ページ作成」提案 | 閲覧者向けサイトには不要 |
| 404ページ固有の検索UI | 共通ヘッダーに検索ボックスが常設されているため |
| RSS/Atom `/feed.xml` | 優先度低の nice-to-have。初期リリースには含めない |
| ライトボックスのズーム・パン・前後ナビ・キャプション | シンプル版で十分（§5.3） |

## 付録: 実装メモ（CSSの罠）

**コードブロック内の行ごとに丸角ボックスが出る**

地の文用インラインコード `.body code { background; border-radius; padding }` と、コードブロック用の打ち消し `pre code { background: none }` が競合し、詳細度（`.body code` = クラス1+要素1 > `pre code` = 要素2）で前者が勝っていた。`<code>` はインライン要素なので、背景色が残ったまま複数行に折り返されると行ごとに独立した角丸ボックスとして描画される。打ち消し側を `.body pre code` にして詳細度を逆転させて解決。

→ 同じ要素に文脈違いのスタイルを当てるときは、詳細度を先に計算してから書く。

**ライトモードでコードブロックの文字色が白飛びする**

上記の修正時に `pre code` の文字色を Mocha 固定の変数で直書きしてしまい、テーマ切り替えに追従しなかった。`--code-ink` という意味変数をダーク／ライト双方の `:root` に定義して参照するように変更。

→ 色を触るたびに、◐ボタンでテーマを一往復させてから確認する。
